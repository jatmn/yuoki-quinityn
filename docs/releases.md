# Releases and nightlies

Release Please starts from **0.1.0** and proposes **0.1.1** first. The configured
policy increments the patch for each release, including feature changes. A future
minor/major release needs an intentional policy change. Existing preview tags
and their assets are preserved.

## Two changelogs

- `changelog.txt` is manually maintained for players, the game and Mod Portal.
  Release Please never edits it. Include gameplay, compatibility and installation
  changes; omit CI and development-only maintenance.
- `docs/CHANGELOG.md` is generated by Release Please for GitHub. It includes
  Conventional Commit sections for features, fixes, CI, documentation, tests,
  builds and maintenance, and does not ship in the mod ZIP.

Before merging a release PR, prepend a section to `changelog.txt` whose version
matches that PR's `info.json`. Preserve older sections. Use exactly 99 hyphens,
then `Version: x.y.z`, optionally `Date: YYYY-MM-DD`, two spaces before category
names ending in a colon, and four spaces before `- ` entries. Continuation lines
use six spaces. Prefer recognized categories such as Features, Bugfixes, Changes
and Compatibility. The [official format](https://lua-api.factorio.com/latest/auxiliary/changelog-format.html)
describes the complete rules.

It is expected that a new release PR's package check fails until its manually
written notes are present. Wait for any running Release workflow to finish
before committing notes on that release PR's branch. Once its diff includes
`changelog.txt`, the workflow pauses bot PR refreshes, preserving your notes.
Release Please otherwise rebuilds its branch from main and would discard manual
commits. Merge the prepared release PR when ready. If more work merges into main
while the PR is prepared, refresh the PR and reapply its manual notes so both
changelogs describe everything that will be included in the release.
To resume automatic refresh, first save the manual notes, restore changelog.txt
to main's contents on the release branch, and run Release again.
For a release containing only development changes,
the maintainer can explicitly note that there are no player-facing changes.
Do not add a future version section to ordinary main-branch development: its
top changelog version must match the committed mod version.

## GitHub setup and stable releases

The Release workflow runs on main pushes and can be run manually. Configure a
repository-scoped `RELEASE_PLEASE_TOKEN` secret with contents, pull-request and
issues write access to let bot PR checks run automatically. Alternatively, use
the built-in GITHUB_TOKEN, enable **Allow GitHub Actions to create and approve
pull requests**, and approve the bot PR's workflow runs manually. No token is
committed; the workflow declares its own write permissions.

Merge normal work into main with Conventional Commit subjects. Release Please
maintains a release PR updating the manifest, `.github/version.txt`, `info.json`
and GitHub notes. Add the manual game notes, review the complete PR, and run:

```sh
python3 tools/test_releases.py
python3 tools/package.py
python3 tools/validate_package.py
```

After the maintainer merges the release PR, Release Please tags the release.
Publishing checks out that exact tag, validates it, and attaches only the addon
ZIP and SHA256SUMS to GitHub. Both archive name and internal folder derive from
the packaged info.json. Portal publication uses these same bytes. If the
Factorio key is absent, GitHub publication succeeds and the job reports that the
portal is not connected. A normal feature merge does not publish a stable mod.

The release workflow calls publishing directly: a release created using
GITHUB_TOKEN does not trigger a separate release-event workflow. See
[GitHub's current triggering rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

## Connect Factorio later

No Factorio credentials are needed to merge this automation or use GitHub
releases/nightlies. When ready:

1. Make the required Factorio 2.1 Yuoki/Engines builds available to users. Their
   publication is managed separately; this repository uploads only Quinityn.
2. On the [Factorio profile](https://factorio.com/profile), create an API key for
   the account allowed to manage Quinityn. Add it as the repository Actions
   secret `FACTORIO_API_KEY`. It needs **ModPortal: Upload Mods**; if this will
   create Quinityn's first listing, also grant **ModPortal: Publish Mods**.
3. For first publication, create/select a [custom portal license](https://mods.factorio.com/licenses)
   reflecting the repository's CC BY-NC-SA 4.0 license and NOTICE exceptions.
   Set the repository Actions variable `FACTORIO_LICENSE_ID` to its API identifier,
   `custom_<ID>`. This is required only when the listing does not exist. The
   initial listing uses the mod description, content category and repository
   source link; screenshots and longer presentation can be edited on the portal.
4. Merge the next prepared release PR. The workflow creates the listing if
   absent, or uploads a new version if present. It verifies the portal's version,
   filename and SHA1 against the uploaded ZIP.

The workflow never reads the upload key for nightlies or PR validation. Connecting
the key enables portal publishing for future stable releases without a code edit.
It does not retroactively upload every GitHub release.

Sources: [upload API](https://wiki.factorio.com/Mod_upload_API),
[first publication API](https://wiki.factorio.com/Mod_publish_API),
[license identifiers](https://wiki.factorio.com/Mod_details_API).

## Nightlies

The Nightly workflow runs daily at **08:23 UTC** (01:23 Pacific daylight time,
00:23 Pacific standard time), or manually on main. It builds only Quinityn, with
the source version's next patch: main 0.1.0 produces nightly 0.1.1; after stable
0.1.1 merges, nightlies become 0.1.2. It stamps info.json and a minimal development
notice inside the archive without changing tracked files or generating gameplay
notes. The hand-written history remains below that notice.

Factorio supports only three numeric components, each at most 65535. Neither
four-part versions nor prerelease suffixes can be used in info.json. Unique
`nightly-<UTC date>-<commit>-<run ID>` GitHub tags identify builds; releases are
marked prerelease and are not Latest. They never go to the portal.

Successive nightlies before a stable release share an in-game version. Replace
the previous ZIP; do not keep competing copies. Returning to stable at the same
version also needs manual replacement, and version-based migrations will not run
again for that same version. Use development saves/backups. Dependencies are
obtained separately using the [development guide](development.md).

Local equivalent:

```sh
python3 tools/package.py --nightly --output build/nightly
python3 tools/validate_package.py --nightly --output build/nightly
```

## Retry a partial publication

GitHub and Factorio are separate services. If an upload fails, run **Release**
manually on main with its existing stable tag, for example `v0.1.1`. This also
lets you publish an existing stable GitHub release after connecting the portal.
Do not bump the version or move a tag to retry.

The workflow rejects draft/prerelease tags and tags outside main history. It
rebuilds the exact tagged source and compares any existing GitHub assets byte for
byte before proceeding. Different bytes fail instead of replacing the asset.
On the portal, the same version is accepted as already complete only if its ZIP
hash matches; a conflict fails. Publishing an older missing version after a
newer portal version also fails. A network timeout may occur after the server
accepts an upload, so retry the same tag to verify its state.

## Validation limits

Package validation checks the real archive, notices, source bytes, version
records, Factorio changelog grammar and checksum. Release tests cover normal
and nightly builds, malformed notes/metadata, and simulated portal responses
for first uploads, retries and failures. They do not upload publicly or prove
credentials, portal availability, or in-game gameplay. Existing engine tests
and their change-specific requirements still apply to gameplay changes.
